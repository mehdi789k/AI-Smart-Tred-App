# P0.1 Demo E2E Execution Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete and verify the fail-closed Python–ZeroMQ–EA–Demo execution path while keeping the single real Demo order behind an explicit operator gate.

**Architecture:** Keep `LiveOrderWorkflow` as the only Python order boundary, use `MQL5ExecutionGateway` for one correlated request at a time, and let the EA apply independent MQL5 risk gates. Persist order intent and execution control in the existing repository, then reconcile ambiguous outcomes using read-only MT5 history. No automatic order retry is introduced.

**Tech Stack:** Python 3.12, FastAPI, pytest, pyzmq, SQLAlchemy/PostgreSQL, MetaTrader5 Python package, MQL5 strict mode, Strategy Tester.

**Spec:** [docs/superpowers/specs/2026-09-18-p0-1-demo-e2e-design.md](../specs/2026-09-18-p0-1-demo-e2e-design.md)

## Global Constraints

- `MT5_AUTO_TRADING_ENABLED=false` remains the default and automated loops stay disabled during validation.
- Timeout, malformed response, and unknown broker outcome are never accepted and never retried automatically.
- Only `XAUUSD_l`, `BUY`, `0.02`, approved protection prices, and magic `26090901` are allowed for the bounded scenario.
- The daily-loss circuit breaker is `10 USD`; an unconfigured durable control store blocks execution.
- The final order-send boundary requires a short-lived confirmation token whose action hash includes symbol, side, volume, SL, and TP.
- No credential, account login, password, or server secret is written to source, fixtures, logs, or reports.
- Do not claim broker acceptance or reconciliation until fresh terminal evidence exists.
- Do not send a real Demo order during automated tests or without a new final operator confirmation.
- Keep implementation code under `src/`, tests under `tests/`, and evidence under `reports/`.
